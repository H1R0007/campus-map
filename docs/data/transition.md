# Переходы (`transitions.json`)

Переход соединяет узлы разных этажей или разных корпусов: лестница, лифт, вход, надземный проход. Связи внутри одного этажа лежат в `neighbors` узла — см. [Узел](node.md).

```json
{
  "transitions": [
    { "from": { "node": "a1_stairs" }, "to": { "node": "a2_stairs" }, "transition_type": "stairs" }
  ]
}
```

## Типы

| Тип | Что это | Значок в интерфейсе |
| --- | --- | --- |
| `entrance` | вход / выход из корпуса, связывает территорию и этаж | дверь |
| `stairs` | лестница между этажами | лестница |
| `lift` | лифт | лифт |
| `bridge` | переход между корпусами (надземный или подземный) | мост |

Тип не указан — `entrance`. Неизвестный тип приводится к `entrance` **с предупреждением**: потерять связность графа из-за опечатки хуже, чем построить маршрут через вход.

Устаревшие названия из ранних версий формата читаются, но никогда не пишутся:

| Устаревшее | Каноническое |
| --- | --- |
| `door` | `entrance` |
| `elevator` | `lift` |
| `passage` | `bridge` |

## Переход ненаправленный

Из `from` можно идти в `to` и обратно. Переход попадает в список смежности графа с обеих сторон, а повторная запись того же ребра (в любом порядке концов) игнорируется — ключ ребра канонический (`edgeKey` сортирует концы).

## Что даёт переход, кроме связи

- **`isPortal` у узлов.** Точки, участвующие в переходах, помечаются автоматически, и навигатор рисует их отдельным слоем со значком типа. Отдельной галочки «точка перехода» у разметчика нет: это следствие (запись 43).
- **Стоимость маршрута.** У каждого типа свой вклад во время пути; лестница и лифт считаются по-разному, и от этого зависит, какой маршрут выберет A*. Модель — в `packages/core/src/pathfinding/costModel.ts`.
- **Ограничения маршрута.** Навигатор умеет искать «без лестниц», «без лифтов», «без переходов между корпусами». Если путь при ограничениях не найден, он предлагает снять ограничение, а не молчит.
- **Выход из корпуса.** Отдельной отметки «выход» в данных нет: выход — это вход, заведённый переходом `entrance`. Навигатор находит ближайшую дверь сам. Прежняя отметка вида места `exit` снимается загрузчиком с объяснением.

## Лестница — цепочка, а не один переход

Лифт и лестница в данных описаны переходами между **соседними** этажами: `a1_lift ↔ a2_lift`, `a2_lift ↔ a3_lift`. Поездка на пятый этаж — это цепочка переходов, и поиск это учитывает: ожидание лифта входит в стоимость один раз на поездку, а не на каждый этаж. Иначе лифт проигрывал бы лестнице ровно там, где он нужнее всего.

Для инструкций цепочка сворачивается в один шаг: «Поднимитесь на лифте — Этаж 5», а не пять одинаковых.

## Как это делается в редакторе

Два способа, оба в режиме «Разметка»:

- **Инструмент «Переход» (клавиша `T`), щелчок по пустому месту плана.** Точки встают сразу на все этажи корпуса и связываются переходами: так заводится лестница или лифт, проходящие через все этажи.
- **Щелчок по существующей точке или «Переход отсюда…» в свойствах.** Справа открывается план, где обычно второй конец; между концами тянется пунктир. Так делаются вход и переход между корпусами: второй конец может быть на территории или в другом корпусе.

## Что проверять

| Симптом | Причина |
| --- | --- |
| Этаж — отдельный «остров», маршруты к нему не строятся | нет ни одного перехода с этим этажом |
| Маршрут ведёт через вход, хотя есть прямой путь | переход потерян или тип перепутан |
| На карте у лестницы нет значка | узел не участвует в переходах, `isPortal` снят |
| «Проверка → Готовность»: «Этажи корпусов соединены» не выполнено | лестница или лифт есть не на всех этажах корпуса |

Проверить связность и увидеть, что именно не так, можно в редакторе («Проверка → Замечания») или командой `pnpm test`: тест на реальном `data/` падает, если граф распался на компоненты.
