# Проверки и тесты

Шесть уровней проверок. Каждый ловит то, что не ловят остальные, поэтому «тесты прошли» означает прогон всех шести, а не `pnpm test` в одиночку.

| Уровень | Команда | Что ловит |
| --- | --- | --- |
| типы | `pnpm typecheck` | расхождение типов между пакетами, неполный словарь переводов |
| линтер | `pnpm lint` | правила проекта, запреты из `DECISIONS.md` |
| модульные тесты | `pnpm test` (Vitest) | логика ядра, редактора и навигатора на данных в памяти |
| сверка сборки | внутри `pnpm test` | датасет в `dist` совпадает с `data/`, лишних файлов нет |
| смоук-тесты | внутри `pnpm test` | раздача по HTTP: коды ответов, отсутствующий файл — 404, а не HTML |
| сценарии в браузере | `pnpm check:browser` | то, что видно только при нажатиях |
| сборка документации | `pnpm docs:build` | битая ссылка, устаревшая карта разделов |

## Модульные тесты

| Пакет | Что проверяет | Файлы |
| --- | --- | --- |
| `core` | загрузка и нормализация, граф, поиск пути, привязка, алиасы, повороты, панорамы | `packages/core/tests/` |
| `mapkit` | обвязка карты: камера, рамки, размеры плана | `packages/mapkit/tests/` |
| навигатор | стор, поиск, шаги, ссылки, кэш, склонения | `apps/viewer/tests/` |
| редактор | история, правка, структура, импорт, готовность, фото | `apps/editor/tests/` |
| `tour-lab` | прототип панорам | `apps/tour-lab/tests/` |

Отдельно стоит знать три теста ядра:

| Тест | Что проверяет |
| --- | --- |
| `pathfinding.optimality` | найденный путь действительно кратчайший — сравнение с оракулом |
| `pathfinding.consistency` | на каждом ребре реального датасета `h(a) ≤ stepCost + h(b)` |
| `dataset.real` | реальный `data/` читается без ошибок, связность не нарушена |

Тесты на реальном датасете — это защита от того, что «в коде всё правильно, а данные битые».

## Сверка сборки

```bash
node tooling/verify-dist-data.mjs --app viewer
```

Проверяет две вещи: содержимое `dist/data` совпадает с `data/` и лишних файлов в `dist/data` нет. Именно лишний файл выдаёт вернувшуюся копию датасета внутри приложения — ситуацию, из-за которой приложения начинали видеть разные данные.

## Смоук-тесты

```bash
node tooling/smoke-test.mjs --app viewer --mode prod
node tooling/smoke-test.mjs --app viewer --mode prod --base /campus/
node tooling/smoke-test.mjs --app viewer --mode dev
```

Поднимает сервер и проходит матрицу HTTP-проверок: главная страница, датасет, планы, фото, ответы на отсутствующие файлы, выход за каталог. Проверяет то, чего не видно в модульных тестах: как приложение ведёт себя с сервером.

## Сценарии в браузере

```bash
pnpm build
pnpm check:browser
pnpm check:browser -- --app viewer --only навигация
```

38 сценариев: 28 редактора и 10 навигатора. Идёт минуты, требует установленного Chrome или Edge. Как писать и отлаживать — [Сценарий в браузере](../recipes/browser-scenario.md).

## Документация

```bash
pnpm docs:style
pnpm docs:export
pnpm docs:build
```

Сборка падает, если:

- внутренняя ссылка ведёт в никуда;
- карта разделов в `docs/index.md` и `docs/README.md` не пересобрана после добавления страницы;
- в прозе встретился запрещённый оборот.

Внешние ссылки проверяются глазами: в CI нет сети, поэтому недоступный внешний адрес сборка не заметит.

`pnpm docs:style` — проверка стиля: список запрещённых оборотов в `tooling/docs-style.mjs`, рядом с каждым правилом причина. Код возврата 1 только на правила уровня «ошибка»; замечания печатаются и не валят сборку.

Правило добавляется, когда оборот действительно мешает читать: оценка вместо факта, обращение к читателю, рекламная формулировка. Отключать проверку целиком из-за одного ложного срабатывания не нужно — правится список, а причина записывается рядом с правилом.

## Что делает CI

`.github/workflows/ci.yml`, две задачи:

| Задача | Что делает |
| --- | --- |
| Сборка, типы, линтер, тесты | установка с `--frozen-lockfile`, `build`, `typecheck`, `lint`, `test`, затем сборка навигатора с `CAMPUS_BASE_PATH=/campus/` и смоук-тест под подкаталогом |
| Сценарии в браузере | все сценарии в свежем Chrome и в закреплённом Chrome 130 |
| Документация | карта разделов, стиль прозы, сборка сайта и переносимого файла |

Подкаталог проверяется на каждом прогоне намеренно: без этого расхождение всплыло бы только при развёртывании.

Chrome 130 закреплён потому, что ошибка с PDF проявлялась только в браузере постарше: у владельца был свежий Chrome, и вручную её никто не видел.

Повторный пуш в ту же ветку отменяет устаревший прогон: проверка нужна на актуальном состоянии.

## Перед коммитом

```bash
pnpm build && pnpm typecheck && pnpm lint && pnpm test
```

Если менялись данные или интерфейс — добавить `pnpm check:browser`. Если документация — `pnpm docs:build`.

## Что делать при провале

| Провал | Первое действие |
| --- | --- |
| типы | прочитать сообщение: часто это забытое поле в сохранении или неполный словарь |
| линтер | правило, а не вкус: если правило мешает, обсуждается его изменение, а не отключение |
| `dataset.real` | посмотреть предупреждения загрузчика: они перечисляют файл, точку и поле |
| `pathfinding.consistency` | в модель стоимости добавили что-то, что уменьшает шаг или переоценивает остаток |
| сверка `dist/data` | в приложении появилась копия датасета: удалить `apps/*/public/data` |
| смоук-тест | проверить `CAMPUS_BASE_PATH`: чаще всего сборка и проверка запущены с разными путями |
| сценарий в браузере | повторить с `--shots` и посмотреть снимок; текст интерфейса мог измениться |
| сборка документации | сообщение указывает файл и ссылку; карту разделов пересобрать `pnpm docs:map` |

## Чего не делать

- Не отключать проверку, которая «мешает»: у каждой в проекте есть история дефекта.
- Не запускать сценарии в браузере без `pnpm build`: они работают по прод-сборке.
- Не коммитить `pnpm-lock.yaml` частично: CI ставит `--frozen-lockfile`.
- Не править `data/` руками, если данные собирает генератор: см. [Карта репозитория](../architecture/repo-map.md).
