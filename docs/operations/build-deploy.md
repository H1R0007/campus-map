# Сборка и развёртывание

Что собирается, куда кладётся, от каких переменных окружения зависит и как убедиться, что собранное будет работать там, куда его поставят.

## Что и куда собирается

```bash
pnpm build
```

| Что | Результат |
| --- | --- |
| `packages/core`, `packages/mapkit` | `dist/` внутри пакета — приложения подключают именно его |
| навигатор | `apps/viewer/dist/` — статика (HTML, JS, CSS, PWA-ассеты) + `dist/data/` |
| редактор | `apps/editor/dist/` — то же |
| документация | `docs/dist/` — статический сайт |

Порядок задаёт turbo: `build` зависит от `^build`, поэтому пакеты собираются раньше приложений.

## Датасет попадает в сборку

В прод-сборке плагин `tooling/vite-plugin-campus-data.mjs` кладёт `data/` в `dist/data/`. Отдельного шага «скопировать данные» нет и не должно быть: копия в `public/` сделала бы Vite вторым писателем, и результат зависел бы от порядка.

Сверка после сборки:

```bash
node tooling/verify-dist-data.mjs --app viewer      # dist/data == data/, лишних файлов нет
```

Именно **лишний** файл в `dist/data` выдаёт вернувшуюся копию датасета внутри приложения, поэтому скрипт проверяет и совпадение, и отсутствие мусора. Он входит в `pnpm test`.

## Базовый путь развёртывания

По умолчанию сборка рассчитана на корень домена. Для подкаталога:

```bash
CAMPUS_BASE_PATH=/map/ pnpm build          # в PowerShell: $env:CAMPUS_BASE_PATH='/map/'
```

Переменная задаёт `base` для Vite; в коде используется `import.meta.env.BASE_URL` через `src/config/dataBase.ts`. От неё зависят URL датасета, `start_url` манифеста PWA, `navigateFallback` service worker и правила кэширования — поэтому «собрать как получится» нельзя.

Проверить сборку под подкаталогом:

```bash
CAMPUS_BASE_PATH=/campus/ pnpm --filter @campus-map/viewer build
node tooling/smoke-test.mjs --app viewer --mode prod --base /campus/
```

Обратите внимание: базовый путь передаётся и в сборку, и в проверку **отдельно**. Это намеренно — молчаливое расхождение между ними дало бы зелёный прогон на неверно собранном приложении. CI проверяет оба варианта на каждом прогоне.

Документация ведёт себя так же: `DOCS_BASE_PATH=/campus-map/ pnpm docs:build`.

## Переменные окружения

| Переменная | Что задаёт | По умолчанию |
| --- | --- | --- |
| `CAMPUS_BASE_PATH` | базовый путь приложений | `/` |
| `CAMPUS_DATA_DIR` | другой каталог данных (синтетический кампус, эксперимент) | `<repo>/data` |
| `CAMPUS_PHOTOS_DIR` | общая папка фото точек | нет — только `data/photos/` |
| `CAMPUS_SOURCES_DIR` | каталог присланных оригиналов планов (редактор) | `<repo>/data-sources` |
| `CAMPUS_UPLOADS_DIR` | куда складывать загрузки до сохранения | временный каталог системы |
| `CAMPUS_SANDBOX_DIR` | каталог учебной копии | `<repo>/.local/sandbox` |
| `CAMPUS_PANORAMAS_DIR` | снимки 360° для прототипа | `.local/panoramas` |
| `DOCS_BASE_PATH` | базовый путь документации | `/` |

Личные значения удобно держать в `.env.local` в корне репозитория — файл в git не попадает:

```text
CAMPUS_PHOTOS_DIR=D:/Яндекс.Диск/campus-photos
```

## Планы, фото и оригиналы

- **Планы этажей** лежат в `data/` и попадают в сборку вместе с датасетом — это часть карты.
- **Фото точек**: в сборку кладутся только те, на которые ссылаются точки; недостающие сборка перечисляет списком (обычно это незаконченная синхронизация общей папки). `verify-dist-data.mjs` сверяет их с общей папкой.
- **Оригиналы планов** (`data-sources/`) в сборку **не попадают**: это внутренний материал для переделки плана. Редактор читает их на dev-сервере.

## PWA-ассеты

Иконки в `apps/viewer/public/` сгенерированы и закоммичены, чтобы сборка не зависела от шага кодогенерации. При смене фирменного стиля:

```bash
node tooling/generate-pwa-assets.mjs
```

Править PNG руками не нужно. В precache попадает только оболочка приложения: планы и JSON датасета кэшируются на лету, потому что официальные планы заметно тяжелее тестовых и тянуть их в установочный пакет нецелесообразно.

## Документация

```bash
pnpm docs:dev                       # живая перезагрузка, http://localhost:3003
pnpm docs:build                     # статика в docs/dist
DOCS_BASE_PATH=/campus-map/ pnpm docs:build
```

Сборка падает на битой внутренней ссылке — это и есть проверка актуальности. Разворачивать `docs/dist` можно любым статическим сервером или GitHub Pages.

## Проверка перед публикацией

```bash
pnpm build && pnpm typecheck && pnpm lint && pnpm test
pnpm check:browser                  # после build, идёт минуты, нужен Chrome или Edge
```

| Проверка | Что ловит |
| --- | --- |
| `typecheck` | расхождение типов между пакетами |
| `lint` | правила проекта, в том числе запреты из `DECISIONS.md` |
| `test` | тесты ядра, навигатора, редактора; сверка `dist/data`; смоук-тесты раздачи |
| `check:browser` | то, что видно только при нажатиях: фокус, контекстные меню, приближение, офлайн, темы, контраст |

В браузере нужен установленный Chrome или Edge; другой браузер — переменной `CAMPUS_BROWSER`. В облаке, например: `CAMPUS_BROWSER=/opt/pw-browsers/chromium pnpm check:browser`.

## Что делает CI

`.github/workflows/ci.yml`, две задачи:

1. **Сборка, типы, линтер, тесты** — установка с `--frozen-lockfile`, `pnpm build`, `typecheck`, `lint`, `test`, затем сборка и смоук-тест навигатора под подкаталогом `/campus/`.
2. **Сценарии в браузере** — все сценарии в свежем Chrome и в закреплённом Chrome 130: ошибки, которые видны только в браузере постарше, иначе никто бы не увидел. При провале снимки экрана выкладываются артефактом.

Повторный пуш в ту же ветку отменяет устаревший прогон.

## Развёртывание у вуза: что важно знать

- Сервис должен работать **в изолированной сети**. Внешних CDN, шрифтов и карт нет — это условие, а не пожелание.
- Развёртывание — это статика: любой веб-сервер, отдающий файлы. Никакой серверной части, кроме раздачи, у навигатора нет.
- **Редактор — не для публичного доступа.** «Сохранить» пишет в `data/` только на dev-сервере; в развёрнутой сборке остаётся «Скачать архив», содержимое которого распаковывается в корень репозитория.
- Подкаталог — самый частый сюрприз: если карта открывается, а планы и данные — нет, почти наверняка сборка сделана без `CAMPUS_BASE_PATH`.

## Частые проблемы

| Симптом | Причина и что делать |
| --- | --- |
| Приложение не видит правку ядра | ядро подключено собранным: `pnpm --filter @campus-map/core build` или watch |
| Данные приходят как HTML | запрос `/data/...` не попал в плагин: проверить `sourceDir` и прогнать `smoke-test --mode dev` |
| Нет времени в пути | пиксельный режим: не привязана территория или этаж (см. [привязку](../data/placement.md)) |
| PWA-иконки битые | перезапустить `tooling/generate-pwa-assets.mjs`, а не править PNG |
| `pnpm install` падает на lock-файле | lock версионируется, CI ставит `--frozen-lockfile`: закоммитить обновлённый `pnpm-lock.yaml` |
| Ошибка в документации: битая ссылка | `pnpm docs:build` покажет файл и ссылку |
