# Как устроена эта документация

Страница для того, кто будет править документацию — в том числе через полгода, когда деталей уже не помнит. Здесь правила, которые позволяют менять текст любого размера, и причины, по которым они такие.

## Три формы одних и тех же текстов

| Форма | Где живёт | Для чего |
| --- | --- | --- |
| Markdown в репозитории | `docs/**/*.md` | Основная. Читается на GitHub, правится в том же PR, что и код |
| Сайт | `docs/dist/` — сборка VitePress | Локальный просмотр с поиском; публикация возможна, но не обязательна |
| Один файл | `docs/dist-offline/campus-map-docs.html` | Передача: вузу, подрядчику, в архив проекта |

Источник истины — Markdown. Сайт и файл собираются из него, поэтому расхождение возможно только там, где их не пересобрали. Подробно про передачу — [Три формы документации](transfer.md).

## Принципы

1. **Пишем для читателя, а не для полноты.** У каждой страницы один читатель и один вопрос. «Всё о проекте» на одной странице невозможно поддерживать.
2. **Сначала самое нужное.** Команда, из-за которой страницу открыли, — в начале, подробности ниже.
3. **Показываем, а не рассказываем.** Команда, путь к файлу, фрагмент JSON — вместо описания словами.
4. **Ссылаемся, а не копируем.** Дублирование — главная причина, по которой документация расходится с кодом. Пересказ одного и того же живёт в одном месте.
5. **Устаревшая документация хуже отсутствующей.** Поэтому сборка падает на битой внутренней ссылке и на устаревшей карте разделов, а состояние тем видно в [карте покрытия](coverage.md).

## Правила, которые держат структуру

### Одна тема — один файл

Файл, который предстоит переписать целиком, — это файл, который перепишут неправильно. Раздел «Формат данных» — это `data/layout.md`, `data/node.md`, `data/transition.md` и так далее, а не `data.md` на 2000 строк.

Практическое следствие: правка не требует читать соседние главы, а конфликт в git при параллельной работе возникает только у тех, кто правит одну и ту же тему.

### Ничего не перечисляется в конфиге

Боковая навигация собирается обходом каталога (`docs/.vitepress/sidebar.mjs`):

- **Добавить страницу** — создать файл в разделе. Он сам появится в навигации: название берётся из первого заголовка `# …`, позиция — из поля `order`.
- **Добавить раздел** — создать каталог и одну строку в массиве `SECTIONS` (только там задаётся порядок разделов).
- **Переименовать тему** — переименовать файл и поправить ссылки. Битая ссылка уронит сборку и покажет, где именно.

Поэтому нет ни списка страниц на сотню строк, который забывают обновить, ни нумерации в именах файлов, из-за которой вставка главы в середину тянет за собой переименование всех следующих.

### Карта разделов собирается, а не пишется руками

На GitHub навигации нет — виден только список файлов, поэтому карта всех страниц с описаниями лежит в двух местах: `docs/index.md` (главная страница сайта) и `docs/README.md` (то, что GitHub показывает при открытии каталога). Обе собирает `tooling/docs-map.mjs` из тех же файлов и в том же порядке, что и навигацию сайта: источник один, расходиться нечему.

```bash
pnpm docs:map            # обновить после добавления или переименования страницы
pnpm docs:map --check    # проверить; то же делает pnpm docs:build
```

Описание страницы берётся из поля `description` во фронтматтере — одной строкой, без точки в конце и без сокращений.

```md
---
order: 40
description: "Переходы между этажами и корпусами: виды, стоимость, хранение ребра."
---
```

### Порядок задаётся числом

```md
---
order: 40
---
```

`order` — необязательное поле. Страницы без него идут в конце раздела по алфавиту. Шаг в 10 оставляет место для вставки: вставили главу между 30 и 40 — дали ей 35, ничего не переименовывая.

Название пункта в навигации, в карте разделов и в поиске — первый заголовок файла. Отдельное поле `title` нужно редко, только если заголовок в тексте длиннее, чем хочется в меню.

## Как писать

### Ссылки

- Внутри документации — относительные пути с расширением: `[формат узла](../data/node.md)`. Их понимают и GitHub, и VitePress: сайт превращает такую ссылку в адрес страницы, а на GitHub она открывает файл. Абсолютный путь от корня сайта (`/data/node`) на GitHub ведёт в никуда, поэтому он не используется.
- На журнал решений — текстом, с номером: «запись 67». Ссылку на `DECISIONS.md` давать только полным адресом на GitHub: файл лежит вне каталога документации, и относительная ссылка на него не собирается.
- На код — путём от корня репозитория: `packages/core/src/pathfinding/costModel.ts`. Коммит-хеши и номера строк не пишем: они устаревают молча.
- Внешние ссылки — по делу, с подписью источника. Проверяются глазами: сборка в CI без сети.

### Термины

Интерфейс редактора и данные называют одни вещи по-разному — так решили осознанно (запись 58). В документации держим соответствие:

| В данных и коде | В интерфейсе редактора | Что это |
| --- | --- | --- |
| `graph.json`, «узел» | точка | место на плане |
| `neighbors` | связь | проход между двумя точками одного плана |
| `transitions.json`, «переход» | переход | лестница, лифт, вход, мост между корпусами |
| `placement` | размещение | где корпус стоит на территории |
| — | совмещение | этаж относительно этажа входа |

Первое упоминание на странице — оба названия, дальше то, которое читателю ближе. Техническая страница говорит «узел», руководство разметчика — «точка».

### Осторожно с публичностью

Репозиторий публичный. В документацию не попадают: настоящие адреса и названия корпусов вуза, фамилии, ссылки на внутренние сервисы, пути к общим папкам конкретного человека. Примеры — только на тестовом кампусе (`Корпус А`, `А-305`).

## Как проверить правку

Обычную правку текста видно сразу на GitHub: Markdown отрисован, ссылки между страницами работают. Сборка нужна, чтобы проверить то, что GitHub не проверяет: битые ссылки и устаревшую карту разделов.

```bash
pnpm install            # один раз
pnpm docs:build         # проверка ссылок, карты и сборка сайта
pnpm docs:dev           # сайт с живой перезагрузкой, http://localhost:3003
```

`pnpm build` в корне собирает документацию тоже: если проверки упали, это заметят до публикации, а не после.

## Что считается «готовым»

Страница готова, когда:

- [ ] есть один читатель и один вопрос, на который она отвечает;
- [ ] команды и пути можно скопировать и они работают;
- [ ] нет пересказа того, что уже написано в `DECISIONS.md` или на соседней странице;
- [ ] внутренние ссылки относительные и проходят сборку;
- [ ] заполнено поле `description`, а карта разделов пересобрана (`pnpm docs:map`);
- [ ] в [карте покрытия](coverage.md) отмечено, что тема закрыта.
