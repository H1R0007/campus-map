# Поиск маршрута

Маршрут строит `packages/core/src/pathfinding/`: обход графа в `astar.ts` и модель стоимости шага в `costModel.ts`. Модель отделена от обхода, потому что ею пользуются трое: поиск, разбивка найденного пути на шаги и тест согласованности эвристики.

## Три функции

| Функция | Назначение |
| --- | --- |
| `findPath(graph, startId, endId, options?)` | кратчайший путь между двумя узлами |
| `findNearest(graph, startId, targetIds, options?)` | путь до ближайшей из нескольких целей: «ближайший туалет» |
| `findAlternativePaths(graph, startId, endId, options?, maxPaths?)` | основной путь и до двух альтернатив |

```ts
const result = findPath(graph, 'campus_gate', 'a3_room305', { allowStairs: false });

result.found;            // true
result.path;             // ['campus_gate', …, 'a3_room305']
result.cost;              // то, что минимизировал поиск
result.durationSeconds;   // время в пути, секунды (null в пиксельном режиме)
result.segments;          // шаги с типом перехода и временем участка
```

## Опции поиска

```ts
interface PathfindingOptions {
  allowStairs?: boolean;   // true
  allowLift?: boolean;     // true
  allowBridge?: boolean;   // true
  allowEntrance?: boolean; // true
  preferLift?: boolean;    // false
  maxIterations?: number;  // 50 000
}
```

Значения по умолчанию собраны в `DEFAULT_PATHFINDING_OPTIONS` в ядре. Вызов без аргументов ищет кратчайший путь без ограничений. `maxIterations` — защита от зацикливания на повреждённых данных: на связном графе кампуса поиск укладывается в сотни извлечений.

Комбинации ограничений интерфейс собирает сам: «без лестниц» ставит `allowStairs: false`, «без лифтов» — `allowLift: false`. Запрещённое ребро получает стоимость `Infinity` и в обход не попадает.

## Модель стоимости

Режим выбирается по графу (`graph.isMetric`) и не смешивается.

### Метрический режим — секунды

Стоимость шага складывается из горизонтального пути, перепада высоты и надбавок:

| Составляющая | Значение |
| --- | --- |
| ходьба | расстояние в метрах / 1,3 м/с |
| лестница | перепад / 0,2 м/с (этаж 3,6 м — около 18 с) |
| лифт | перепад / 1,0 м/с |
| ожидание лифта | 30 с, один раз на поездку |
| проход входа | 10 с |

Числа — `WALKING_PROFILE` в `costModel.ts`; это оценки для взрослого пешехода, а не измерения. Оптимальность поиска от них не зависит: она держится на устройстве эвристики.

Ожидание лифта входит только в первый шаг поездки — тот, к которому пришли не на лифте. Иначе поездка на пятый этаж через цепочку переходов ждала бы лифт на каждом этаже.

`preferLift` увеличивает стоимость лестницы втрое. Именно штраф лестнице, а не скидка лифту: скидка опустила бы стоимость ниже времени, за которое расстояние можно преодолеть, и нижняя оценка остатка стала бы неверной.

### Пиксельный режим — условные единицы

| Ребро | Стоимость |
| --- | --- |
| внутри этажа | расстояние в пикселях плана |
| `entrance` | 5 |
| `lift` | 15 |
| `bridge` | 25 |
| `stairs` | 40 |
| между этажами без описанного перехода | 10 000 — ошибка данных, маршрут через такое ребро избегается |

Веса подобраны так, чтобы маршрут не петлял через лишние лестницы, но и не запрещал их.

## Эвристика

| Режим | Оценка остатка |
| --- | --- |
| пиксельный | ноль — поиск работает как алгоритм Дейкстры |
| метрический | прямое расстояние в пространстве кампуса / самую быструю скорость профиля |

В пиксельном режиме любая ненулевая оценка переоценивает остаток: координаты узлов лежат в несвязанных системах разных планов, и поиск перестаёт быть оптимальным.

В метрическом режиме оценка согласованна. Для любого шага `a → b`:

```text
stepCost ≥ (горизонталь + перепад) / FASTEST_SPEED ≥ |ab| / FASTEST_SPEED
```

Каждая часть стоимости — путь, делённый на скорость не больше самой быстрой; надбавки неотрицательны; штрафы стоимость только увеличивают. Отсюда по неравенству треугольника `h(a) ≤ stepCost + h(b)`, а значит, A* находит оптимальный путь.

Делитель — максимум по профилю, а не скорость ходьбы: скоростной лифт высотного корпуса (2–3 м/с) быстрее пешехода, и деление на скорость ходьбы лишило бы поиск оптимальности при таких числах в профиле.

Проверяют это два теста: `pathfinding.consistency` — неравенство на каждом ребре реального датасета, `pathfinding.optimality` — сравнение с оракулом.

## Результат

```ts
interface PathResult {
  found: boolean;
  path: string[];
  cost: number;                    // что минимизировал поиск
  distanceMeters: number | null;   // длина по плану, метры
  durationSeconds: number | null;  // время в пути, секунды
  segments?: PathSegment[];
  reason?: PathFailureReason;
  error?: string;
}
```

Два числовых поля нужны потому, что они не совпадают. `cost` — величина, которую минимизирует поиск, с учётом предпочтений: при `preferLift` лестница в ней дороже, чем в жизни. `durationSeconds` — физика найденного пути, от предпочтений не зависит. Сумма `durationSeconds` по шагам всегда равна полю результата, поэтому время в карточке маршрута сходится со временем в шагах.

В пиксельном режиме оба поля равны `null`: у пикселей разных планов нет ни метров, ни секунд. Раньше поле называлось `totalDistance`, и навигатор делил его на скорость, чтобы показать время.

Причины неудачи:

| `reason` | Значение |
| --- | --- |
| `unknown-start` | начального узла нет в графе |
| `unknown-end` | конечного узла нет в графе |
| `unreachable` | узлы не связаны при заданных ограничениях |
| `iteration-limit` | сработала защита от зацикливания |

`error` — пояснение для разработчика на русском, с id узлов. В интерфейс оно не попадает: навигатор двуязычный, а текст ядра нет.

## Ближайшая цель

`findNearest` делает один поиск до множества целей, а не по одному поиску на каждую: обход останавливается на первой извлечённой цели, и она по построению ближайшая в модели стоимости. Оценки остатка здесь нет — наименьшую из эвристик до всех целей пришлось бы считать на каждом узле, а ближайшая цель обычно рядом.

Цели, которых нет в графе, пропускаются. Если не осталось ни одной, результатом будет `unknown-end`.

## Альтернативные маршруты

`findAlternativePaths` ищет основной путь, затем поочерёдно запрещает каждое его ребро и пересчитывает маршрут. Путь, который существует после запрета и отличается от уже найденных, становится альтернативой. Результаты сортируются по стоимости, число альтернатив — `maxPaths − 1`.

Обход рёбер идёт от старта к финишу, поэтому результат воспроизводим. На графе-дереве альтернатив нет — это корректный результат, а не ошибка.

## Что проверять при правке модели

- Изменение чисел `WALKING_PROFILE` меняет показанное время, но не должно менять выбор пути на тестовых данных без перепадов.
- Новая составляющая стоимости обязана быть неотрицательной и не уменьшать шаг: иначе согласованность эвристики теряется, и `pathfinding.consistency` упадёт.
- Новый тип перехода добавляется в `isAllowed` и в `PIXEL_TRANSITION_WEIGHTS`; пропущенный тип в пиксельной модели даст `undefined` в стоимости.
- Новое поле результата добавляется в `PathResult` и заполняется в обоих режимах: `null` в пиксельном, число в метрическом.
