# Архитектурные решения

Журнал решений в формате «контекст → решение → последствия». Одна запись на
решение, новые сверху. Запись добавляется вместе с кодом, который её реализует,
а не после.

Что сюда попадает: выбор, который дорого отменить, и выбор, который иначе
кто-нибудь добросовестно отменит, не зная причины. Что не попадает: стиль,
именование, всё, что видно из кода.

Формат записи:

```
## N. Заголовок
**Дата** · **Статус:** принято | заменено решением N | отменено
**Контекст** — что заставило решать.
**Решение** — что именно решено.
**Последствия** — что теперь придётся помнить и делать.
```

## 5. Построение маршрута переводит карту туда, где маршрут начинается

**2026-09-13** · **Статус:** принято

**Контекст.** `buildRoute` выставлял только `currentRoute`. Навигатор стартует
в виде кампуса (`activeFloor === null`), а слой маршрута рисует лишь узлы
текущей области видимости — поэтому маршрут между аудиториями отфильтровывался
целиком, и пользователь видел неизменившуюся карту кампуса с подписью
«Маршрут готов». Это первый же сценарий использования: найти аудиторию и
посмотреть, как до неё дойти.

Механизм переключения вида при этом уже существовал — кнопки «Открыть этаж N»
у шагов маршрута. Не хватало только вызова.

**Решение.** После успешного построения стор переводит карту в область
видимости **стартового** узла (`scopeOfNode` из ядра, без разбора полей узла
на месте), а слой маршрута подгоняет viewport под видимый отрезок. Подгонка
повторяется при изменении границ плана: реальный размер картинки определяется
асинхронно, и без этого маршрут «уезжал» ровно в момент догрузки.

Заодно убраны два смежных расхождения:

- правка поля запроса снимает показанный маршрут, если его концы больше не
  совпадают с выбранными точками — иначе карточка печатала новый текст рядом
  со старой линией;
- смена ограничений пересчитывает **уже показанный** маршрут, а не строит
  новый: прежнее условие «обе точки разрешены» создавало маршрут, которого
  никто не просил.

**Последствия.** Концы маршрута нигде не хранятся отдельно — это первый и
последний узел пути. Новое действие, меняющее точки, обязано пройти через
`dropStaleRoute`, иначе расхождение вернётся.

## 4. Датасет живёт в одном экземпляре; копии в приложениях запрещены сборкой

**2026-09-13** · **Статус:** принято

**Контекст.** В `master` оказались две полные копии датасета —
`apps/viewer/public/data/` и `apps/editor/public/data/`, по 20 файлов. Локально
они были замаскированы junction-ссылками на корневой `data/`, поэтому
`git status` показывал чистое дерево, а свежий клон на другой машине получал
настоящие дубликаты. `README` при этом прямо запрещал такие копии.

Механически проблема в том, что каталог `public/` Vite копирует в `dist/` сам, а
`campusDataPlugin` кладёт туда же данные через `emitFile`. Два писателя в один
путь: чьи файлы останутся, зависит от порядка. Проявилось бы это как «в
редакторе видно, в навигаторе нет» — и искалось бы очень долго.

**Решение.** Единственный источник истины — `data/` в корне репозитория.
Копии удалены из индекса и с диска. Запрет держится тремя независимыми
средствами, потому что записи в документации оказалось недостаточно:

1. `.gitignore` — строка `apps/*/public/data/`;
2. `campusDataPlugin` в хуке `configResolved` **падает**, если каталог найден;
3. `tooling/verify-dist-data.mjs` сверяет `dist/data` с `data/` побайтово и
   отдельно ловит **лишние** файлы — именно лишний файл выдаёт вернувшуюся
   копию. Запускается в составе `pnpm test` и в CI.

У редактора собственных статических файлов нет вовсе, поэтому там
`publicDir: false` — каталога, куда можно положить копию, просто не существует.

**Последствия.** Править данные нужно ровно в одном месте. Если копия
появится снова, сборка остановится с объяснением, а не отработает молча.
Удалять junction на Windows нужно через `rmdir` или
`Directory.Delete(path, false)`: `rm -rf` в Git Bash проходит **по ссылке** и
уничтожает настоящие данные.

## 3. Базовый путь развёртывания задаётся снаружи

**2026-09-13** · **Статус:** принято

**Контекст.** Куда вуз поставит сервис — в корень домена или в подкаталог вида
`/map/` — на момент разработки неизвестно. От этого зависят URL датасета,
`start_url` манифеста PWA, `navigateFallback` service worker и правила
кэширования. Всё это было зашито от корня: при развёртывании в подкаталоге
приложение открылось бы, а данные — нет.

**Решение.** `base` в обоих `vite.config.ts` берётся из `CAMPUS_BASE_PATH`, в
коде используется `import.meta.env.BASE_URL`. Точка монтирования плагина данных
выводится из `config.base`, а не из отдельной опции: второй источник истины о
базовом пути разошёлся бы с тем, что Vite подставляет в приложение.
URL-хелперы ядра (`datasetUrl`, `campusMapUrl`, `floorMapUrl`,
`createHttpDatasetSource`) уже принимали `baseUrl` — изменились только
вызывающие стороны, через `src/config/dataBase.ts` в каждом приложении.

Подкаталог проверяется в CI на каждом прогоне, а не «когда понадобится»:
иначе расхождение всплывёт при развёртывании, то есть в худший момент.

**Последствия.** Новый URL к данным собирается только хелперами ядра с
передачей `DATA_BASE_URL`. Строковый шаблон `/data/...` в приложении снова
сломает подкаталог. `turbo.json` объявляет `CAMPUS_BASE_PATH` в `env` задачи
`build` — без этого turbo отдал бы кэш сборки с другим базовым путём.

## 2. Скрипты кроссплатформенные, без обхода через Git Bash

**2026-09-13** · **Статус:** принято

**Контекст.** Скрипты `clean` были написаны как `rm -rf dist *.tsbuildinfo`.
Основная машина разработки — Windows, где нет ни `rm` в cmd/PowerShell, ни
раскрытия `*` оболочкой. Описать в документации «запускайте из Git Bash» —
значит сделать ещё один инструмент обязательным ради удаления каталога.
Вдобавок у приложений скрипта `clean` не было вовсе, поэтому `turbo clean` не
трогал `apps/*/dist`.

**Решение.** `tooling/clean.mjs` на Node: принимает пути, поддерживает `*` в
имени файла, удаляет точки повторного разбора как ссылки, без захода внутрь.
Скрипт `clean` добавлен всем четырём пакетам. Разделены `clean` (артефакты
сборки) и `clean:all` (плюс `node_modules`): первый нужен часто, второй почти
никогда, и путать их дорого.

`&&` в npm-скриптах оставлен: на Windows pnpm выполняет их через `cmd.exe`,
где оператор поддерживается.

**Последствия.** Новые служебные скрипты пишутся на Node в `tooling/`, а не
как команды оболочки. Проверять их нужно на Windows — это основная платформа
проекта.

## 1. Ядро подключается собранным, данные нормализует только загрузчик ядра

**Ранее** · **Статус:** принято (зафиксировано задним числом)

**Контекст.** Записано не по свежему следу, а чтобы решение не выглядело
произвольным для того, кто придёт позже. В проекте успели появиться три
независимых загрузчика данных, разошедшихся между собой и по-разному терявших
поля.

**Решение.** Зависимости идут только внутрь: `apps → mapkit → core`. Ядро не
знает ни о React, ни о Leaflet, ни о сети, ни о файловой системе, и не пишет в
консоль — проблемы возвращает списком `warnings`. Ввод-вывод спрятан за
интерфейсом `DatasetSource`; пайплайн нормализации `loadDataset` существует в
единственном экземпляре. Приложения подключают ядро как обычный пакет, через
`exports` на `dist`, без алиасов на исходники.

**Последствия.** После правки ядра его нужно пересобрать, иначе приложения
работают со старым кодом и ошибки выглядят бессмысленными
(`pnpm --filter @campus-map/core dev` держит watch). Разбирать JSON в
приложении нельзя — нужен ещё один `DatasetSource`, как это сделано для импорта
из ZIP и для тестов.
