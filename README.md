# Карта кампуса

Монорепо двух веб-приложений над общим доменным ядром:

- **Навигатор** (`apps/viewer`) — то, что видит студент: планы этажей, поиск
  аудитории, маршрут с пошаговыми инструкциями. PWA, работает офлайн.
- **Редактор** (`apps/editor`) — внутренний инструмент команды разметки:
  узлы, рёбра, переходы между этажами, алиасы, диагностика данных.

Оба приложения работают с одним каталогом данных `data/` в корне репозитория.

Документ рассчитан на разработчика, который получает задачу и должен понять,
где именно менять код и какие ограничения при этом нельзя нарушать. Раздел
«Как поставить задачу» в конце — про это.

Соседние документы:

- `DECISIONS.md` — журнал архитектурных решений «контекст → решение →
  последствия». Читать, прежде чем отменять что-то, что выглядит странно:
  почти за каждым ограничением здесь стоит конкретный дефект.
- `docs/archive/` — исторические документы. **Не список задач**: аудит от
  сентября 2026 описывает состояние до серии рефакторингов и по большей части
  уже неактуален.

## Быстрый старт

Требуется Node 22 и pnpm 9 (`packageManager` в `package.json` задан явно).

```bash
pnpm install     # зависимости + линковка workspace-пакетов
pnpm dev         # оба приложения: навигатор на :3000, редактор на :3001
```

`pnpm dev` сначала собирает пакеты (`turbo dev` зависит от `^build`), поэтому
отдельно собирать ядро не нужно.

Остальные команды:

| Команда | Что делает |
| --- | --- |
| `pnpm build` | Собирает пакеты в `dist` и приложения в `apps/*/dist` |
| `pnpm typecheck` | Проверка типов во всех пакетах |
| `pnpm lint` | ESLint (плоский конфиг в корне) |
| `pnpm test` | 63 теста ядра (Vitest), сверка `dist/data` с `data/` и смоук-тесты раздачи обоих приложений |
| `pnpm clean` | Удаляет `dist` и `*.tsbuildinfo` во всех пакетах |
| `pnpm clean:all` | То же плюс `node_modules` |

Проверять всё сразу: `pnpm build && pnpm typecheck && pnpm lint && pnpm test`.
То же самое делает CI (`.github/workflows/ci.yml`).

Все служебные скрипты — на Node (`tooling/`), а не команды оболочки: основная
машина разработки в проекте под Windows, и обход через Git Bash не должен быть
обязательным.

### Куда разворачивается

По умолчанию сборка рассчитана на корень домена. Для подкаталога:

```bash
CAMPUS_BASE_PATH=/map/ pnpm build     # в PowerShell: $env:CAMPUS_BASE_PATH='/map/'
```

Переменная задаёт `base` для Vite; в коде используется
`import.meta.env.BASE_URL` через `src/config/dataBase.ts`. От неё зависят URL
датасета, `start_url` манифеста PWA, `navigateFallback` service worker и правила
кэширования — поэтому собирать «как получится» и надеяться нельзя. CI проверяет
оба варианта на каждом прогоне.

Ещё одна переменная — `CAMPUS_DATA_DIR`: позволяет прогнать приложения на другом
каталоге данных (например, на синтетическом наборе целевого объёма), не трогая
канонический `data/`.

## Архитектура

```
data/                        датасет: единственный источник истины о кампусе
│
├── packages/core            доменное ядро (без React, Leaflet, DOM, console)
│   ├── types/               контракт данных: MapNode, Transition, Dataset…
│   ├── dataset/             загрузка и нормализация, раскладка путей
│   ├── graph/               неизменяемый граф с индексами, связность
│   ├── pathfinding/         A*, альтернативные маршруты
│   ├── aliases/             нечёткий поиск по названиям
│   ├── geometry.ts          расстояние, ключи рёбер и этажей
│   └── scope.ts             область видимости карты (кампус / этаж)
│
├── packages/mapkit          общая обвязка Leaflet-карты
│   └── PixelMap             растровый план как подложка + слои поверх
│
└── apps/
    ├── viewer               навигатор (React, zustand, PWA)
    └── editor               редактор разметки (React, zustand, immer)
```

### Правило зависимостей

Зависимости идут только внутрь: `apps → mapkit → core`. Ядро не знает ни о
React, ни о Leaflet, ни о сети, ни о файловой системе.

Всё, что связано с вводом-выводом, спрятано за интерфейсом `DatasetSource`:

```ts
interface DatasetSource {
  readJson(path: string): Promise<unknown | null>;  // null — файла нет
}
```

Ядро принимает уже разобранные данные. Три реализации источника:

| Реализация | Где |
| --- | --- |
| `createHttpDatasetSource()` | ядро; используется навигатором и редактором |
| источник поверх JSZip | `apps/editor/src/utils/importZip.ts` |
| источник поверх ФС | `packages/core/tests/helpers/datasetFixture.ts` |

Пайплайн нормализации (`loadDataset`) при этом существует в одном
экземпляре. **Нормализовать данные вручную в приложении нельзя**: это ровно
та ошибка, из-за которой раньше в репозитории было три независимых
загрузчика, разошедшихся между собой.

### Ядро подключается собранным, не исходниками

Приложения импортируют `@campus-map/core` и `@campus-map/mapkit` как обычные
пакеты — через поле `exports`, указывающее на `dist`. Алиасов на исходники в
конфигах нет и быть не должно.

Порядок сборки задаёт turbo: задачи `dev`, `typecheck`, `lint` и `test`
зависят от `^build`. Следствие, о котором нужно помнить: **после правки ядра
его нужно пересобрать**, иначе приложения увидят старую версию.

```bash
pnpm --filter @campus-map/core build      # разово
pnpm --filter @campus-map/core dev        # или watch-режим на время работы
```

Условие `types` в `exports` обязано стоять первым — иначе TypeScript
резолвит `.js` вместо `.d.ts` и типы пакета теряются.

### Данные раздаёт плагин, а не `public/`

Датасет лежит в корне и подхватывается автоматически через
`tooling/vite-plugin-campus-data.mjs`: в dev и preview он раздаёт файлы
middleware'ом, в прод-сборке кладёт их в `dist/data/`.

**Копий датасета внутри приложений быть не должно.** Это не пожелание: каталог
`public/` Vite копирует в `dist/` сам, поэтому копия делает Vite вторым
писателем в `dist/data/**` — и кто победит, зависит от порядка. Проявляется это
как «в редакторе видно, в навигаторе нет». Запрет держится тремя средствами:
строка в `.gitignore`, падение сборки в самом плагине и сверка `dist/data` с
`data/` в `tooling/verify-dist-data.mjs` (входит в `pnpm test`). Подробности —
запись 4 в `DECISIONS.md`.

> Если копия оказалась junction или симлинком на Windows, удалять её нужно
> через `rmdir` либо `Directory.Delete(path, false)`. `rm -rf` в Git Bash идёт
> **по ссылке** и уничтожает настоящие данные.

Плагин отвечает на любой запрос к `/data/*` сам и не пропускает его в
SPA-fallback. Это принципиально: Vite на неизвестный путь отдаёт
`index.html` с кодом 200, и тогда «этажа нет» из мягкого предупреждения
загрузчика превращается в падение на разборе HTML как JSON. Отсутствующий
файл — 404, выход за каталог — 403, неразбираемый путь — 400.

## Формат данных

### Раскладка

```
data/
├── campus/
│   ├── meta.json         список корпусов + резервный размер карты
│   ├── graph.json        узлы территории кампуса
│   └── map.png           план территории
├── buildings/<building_id>/
│   ├── meta.json         имя корпуса и список этажей
│   └── floors/<floor>/
│       ├── graph.json    узлы этажа
│       └── map.png       план этажа
├── transitions.json      переходы между этажами и корпусами
└── aliases.json          человекочитаемые названия узлов
```

Все пути централизованы в `packages/core/src/dataset/paths.ts`
(`buildingMetaPath`, `floorGraphPath`, `floorMapPath`, …) и там же
URL-хелперы (`datasetUrl`, `campusMapUrl`, `floorMapUrl`). **Склеивать
`/data/...` строковым шаблоном в приложении нельзя** — опечатка молча
превращается в 404.

### Главное правило: `building` и `floor` определяет путь файла

В `graph.json` у узла записаны только `id`, `x`, `y`, `neighbors`,
`isPortal` и необязательный `comment`. Принадлежность корпусу и этажу
загрузчик берёт из расположения файла:

- `campus/graph.json` → `building: "CAMPUS"`, `floor: 0`;
- `buildings/building_a/floors/3/graph.json` → `building: "building_a"`,
  `floor: 3`.

Поля `building` и `floor`, записанные в JSON, игнорируются (в типе
`MapNodeData` они помечены как устаревшие и нужны только чтобы заметить
расхождение). Экспорт редактора их не пишет.

### Узел

```json
{
  "id": "a1_room101",
  "x": 130,
  "y": 250,
  "neighbors": ["a1_corridor"],
  "isPortal": false,
  "comment": "геометрия приблизительная, уточнить у коменданта"
}
```

- `x`, `y` — **пиксели изображения плана**, отсчёт от левого верхнего угла.
  Карта работает в `L.CRS.Simple`, где единица равна пикселю, поэтому
  координаты ложатся на план без пересчёта.
- `neighbors` — узлы того же этажа. Рёбра неориентированы по смыслу, но
  асимметрия допустима (одностороннее движение); диагностика относит её к
  предупреждениям.
- `isPortal` — точка смены этажа или корпуса: лестница, лифт, вход. Такие
  узлы навигатор рисует отдельным слоем с иконкой типа перехода.
- `comment` — рабочая заметка разметчика. На маршрутизацию не влияет и
  студентам не показывается. Правится в панели свойств редактора,
  сохраняется в `graph.json`, участвует в отмене действий. Поле задумано
  именно под перенос официальных данных: помечать спорную геометрию,
  закрытые после определённого часа двери, приблизительные проходы.

### Переход

```json
{ "from": { "node": "a1_stairs" }, "to": { "node": "a2_stairs" }, "transition_type": "stairs" }
```

Типы: `entrance` (вход/выход из корпуса), `stairs`, `lift`, `bridge`
(переход между корпусами). Устаревшие `door`, `elevator`, `passage` читаются
и приводятся к каноническим, неизвестный тип становится `entrance` с
предупреждением — потерять связность графа из-за опечатки хуже, чем построить
маршрут через вход.

Переход соединяет узлы в обе стороны и попадает в список смежности графа.

### Алиасы

```json
{ "id": "a1_room101", "names": ["А-101", "Аудитория 101", "101", "Лекционная 101"] }
```

**Это единственный способ найти помещение в навигаторе.** Узел без алиаса
недостижим из интерфейса: его нельзя выбрать как начало или конец маршрута.
При переносе официальных данных алиасы обязательны для каждого узла, до
которого должен уметь дойти студент.

Поиск нечёткий: нормализует регистр и пунктуацию, ищет по номеру
(`«101» → a1_room101`), по префиксу и переживает набор в неверной раскладке
(`«,bibcjntrf» → библиотека`).

### Именование узлов

Соглашение, которое уже соблюдено в данных и по которому удобно искать:

| Область | Шаблон | Примеры |
| --- | --- | --- |
| Территория | `campus_<место>` | `campus_gate`, `campus_square` |
| Этаж | `<корпус><этаж>_<место>` | `a1_room101`, `b2_lab`, `c1_pool` |
| Лестница/лифт | `<корпус><этаж>_stairs`, `_lift` | `a1_stairs`, `a3_lift` |
| Вход | `<корпус><этаж>_entrance` | `a1_entrance` |

Редактор для новых узлов предлагает автоматические id вида
`<корпус>_<этаж>_node_<номер>`. Их стоит переименовывать в понятные: по
автоматическим невозможно ни найти узел в данных, ни понять, что он
означает, — именно так в датасете однажды появился мусорный треугольник
`building_a_1_node_1/2/3`.

## Как добавить корпус или этаж

Задача, которая чаще всего будет делегироваться. Данные правятся напрямую,
редактор для этого не обязателен.

**Новый этаж в существующем корпусе:**

1. Создать `data/buildings/<id>/floors/<номер>/` и положить туда `map.png`
   (план этажа) и `graph.json` с узлами.
2. Добавить запись в `floors` в `data/buildings/<id>/meta.json`:
   `{ "floor": <номер>, "mapPath": "map.png", "graphPath": "graph.json" }`.
3. Связать этаж с соседними переходами в `data/transitions.json`
   (лестница или лифт). Без этого этаж окажется изолированной компонентой.
4. Прописать алиасы в `data/aliases.json` для всех узлов, доступных из
   поиска.
5. Проверить: `pnpm test` (тесты ядра читают реальный `data/` и падают на
   нарушении связности и нормализации), затем `pnpm dev` и посмотреть этаж
   в редакторе — панель диагностики покажет висячие ссылки и асимметрию.

**Новый корпус:**

1. `data/buildings/<id>/meta.json` с именем и списком этажей.
2. Этажи — как выше.
3. Запись в `buildings` в `data/campus/meta.json`.
4. Узел входа на территории кампуса в `campus/graph.json` и переход типа
   `entrance` между ним и узлом `<id>1_entrance`.
5. Алиасы.

Ничего в коде менять не нужно: количество корпусов и этажей не зашито
нигде. Граф индексирует узлы по «корпус#этаж» в конструкторе, поэтому
рост объёма данных не меняет стоимость типовых операций.

### Замена тестовых планов на официальные

Текущие `map.png` — случайные изображения-заполнители, они нужны только
чтобы доказать работоспособность конвейера. При замене:

1. Положить новые `map.png` поверх существующих. **Размер в метаданных
   править не нужно**: пиксельную геометрию карта берёт из самого
   изображения (`useImageSize` в mapkit), а `mapSize` в `campus/meta.json` —
   только резерв на случай недоступной картинки.
2. Пересчитать координаты узлов под новые планы. Проще всего это делать в
   редакторе: он показывает план с реальной геометрией, есть привязка к
   сетке и групповое перемещение.
3. Узлы, в которых геометрия пока приблизительная, помечать полем `comment`
   — оно для этого и существует.

## Ключевые инварианты

Нарушение любого из них уже приводило к дефектам.

**`Graph` неизменяемый.** Все индексы строятся один раз в конструкторе:
`nodes` (id → узел), `nodesByFloor` («корпус#этаж» → узлы),
`transitionsByKey` (ключ ребра → переход), `adjacency` (id → объединённый
список соседей). Мутационного API нет намеренно — он позволял
рассинхронизировать индексы с содержимым. Редактор хранит собственное
мутабельное состояние и собирает новый `Graph` перед каждым поиском пути:
`new Graph(nodes.values(), transitions)`.

**Связность считает только ядро.** `findConnectedComponents` — единственный
обход графа. Собственная копия в редакторе для каждого узла перебирала весь
массив переходов, то есть работала за O(N·T).

**Область видимости — доменное понятие.** `ViewScope` — либо
`{ mode: 'campus' }`, либо `{ mode: 'floor', buildingId, floor }`. Правило
«какие узлы показывать» задано один раз: `scopeOfFloor` (из выбранного
этажа), `scopeOfNode` (из узла), `isNodeInScope` (фильтр). И слои карты
навигатора, и оверлеи редактора пользуются ими.

**Состояние не дублируется.** Производные значения вычисляются, а не
хранятся. В навигаторе нет отдельного флага режима просмотра: он полностью
выводится из `activeFloor`. В редакторе комментарий узла живёт в
`MapNode.comment`, а не в отдельной карте. Хранимый дубль источника истины
рано или поздно расходится.

**Опции маршрутизации по умолчанию — в ядре.**
`DEFAULT_PATHFINDING_OPTIONS`. Свой экземпляр в приложении заводить не надо.

**Ядро не печатает в консоль.** Проблемы в данных возвращаются списком
`warnings` из `loadDataset`, а что с ними делать, решает приложение:
навигатор пишет их в консоль, редактор показывает в панели диагностики.

**Никаких внешних CDN.** Стили Leaflet импортируются из npm-пакета, шрифты —
системные. Сервис, развёрнутый у вуза, обязан работать в изолированной сети,
а загрузка шрифта с `fonts.googleapis.com` означала ещё и передачу IP-адреса
третьей стороне, что для развёртывания в ЕС неприемлемо.

## Проверки

**Тесты ядра** — `packages/core/tests`, 63 проверки в шести файлах
(`dataset`, `graph`, `pathfinding`, `connectivity`, `aliases`, `scope`).
Импортируют исходники, а не `dist`: Vitest резолвит `.js`-спецификаторы в
`.ts`, поэтому сборка перед прогоном не нужна. Данные берутся из реального
`data/` через тот же `DatasetSource`, через который их читают приложения, —
иначе тесты разошлись бы с продуктом.

Отдельно зафиксирован инвариант, который раньше был нарушен: сумма
стоимостей шагов маршрута обязана равняться `totalDistance` при любых
опциях, включая `preferLift`.

**Смоук-тесты раздачи** — `tooling/smoke-test.mjs`, запускаются как
`pnpm test` в приложениях. Поднимают прод-сборку (32 проверки у навигатора,
24 у редактора) и проверяют оболочку, PWA-ассеты, данные, честный 404
вместо SPA-fallback, отказ на обход каталога и работу клиентской
маршрутизации. Запросы идут через `node:http` с дословным `path`: WHATWG URL
нормализует `..` до отправки, и проверки обхода каталога стали бы
бесполезными.

Проверить раздачу в dev-режиме вручную:
`node tooling/smoke-test.mjs --app viewer --mode dev`.

Тот же набор под подкаталогом — базовый путь передаётся отдельно и намеренно
не выводится из окружения: сборка и проверка это разные запуски, и молчаливое
расхождение между ними дало бы зелёный прогон на неверно собранном приложении.

```bash
CAMPUS_BASE_PATH=/campus/ pnpm --filter @campus-map/viewer build
node tooling/smoke-test.mjs --app viewer --mode prod --base /campus/
```

**Сверка датасета** — `tooling/verify-dist-data.mjs` сравнивает `dist/data` с
корневым `data/` по содержимому и отдельно ловит **лишние** файлы: именно
лишний файл выдаёт вернувшуюся копию данных внутри приложения.

**CI** — `.github/workflows/ci.yml`: установка с `--frozen-lockfile`,
сборка, типы, линтер, тесты.

## Как поставить задачу

Что где менять, чтобы задача не ушла не туда.

| Задача | Где |
| --- | --- |
| Логика маршрута, стоимость рёбер, типы переходов | `packages/core/src/pathfinding/`, `types/transition.ts` |
| Формат данных, нормализация, новые поля датасета | `packages/core/src/types/`, `dataset/loader.ts` |
| Поведение карты как таковое (зум, подложка, границы) | `packages/mapkit/src/PixelMap.tsx` |
| Интерфейс навигатора, панели, карточка маршрута | `apps/viewer/src/components/UI/` |
| Слои навигатора (маркеры, порталы, линия маршрута) | `apps/viewer/src/components/Map/` |
| Пошаговые инструкции маршрута | `apps/viewer/src/utils/routeInstructions.ts` |
| Инструменты разметки и панели редактора | `apps/editor/src/components/` |
| Действия редактора и отмена | `apps/editor/src/stores/editorStore.ts`, `historyStore.ts` |
| Импорт/экспорт датасета | `apps/editor/src/utils/importZip.ts`, `exportData.ts` |
| Валидация данных для панели диагностики | `apps/editor/src/utils/validateData.ts` |
| Раздача данных, сборка, PWA, базовый путь развёртывания | `tooling/`, `apps/*/vite.config.ts` |
| Архитектурное решение и его причины | `DECISIONS.md` |

Два момента, которые стоит проговорить в задаче явно:

- **Новое поле данных** требует правки в четырёх местах, иначе оно
  потеряется: тип в `types/`, чтение в `dataset/loader.ts`, запись в
  `apps/editor/src/utils/exportData.ts` и тест в `packages/core/tests/`.
  Поле, которое читается, но не пишется экспортом, молча исчезает при
  первом же сохранении из редактора.
- **Новое отменяемое действие** в редакторе добавляется как член объединения
  `HistoryEntry` в `stores/historyStore.ts`. Компилятор сам потребует
  обработать его в обеих ветках — и в отмене, и в повторе.

### Что известно как незакрытое

- `apps/editor/src/stores/editorStore.ts` — около 2100 строк в одном файле.
  Работает и типизирован, но декомпозиция на срезы (zustand slice pattern)
  попросится при первом же крупном изменении.
- Отдельных тестов на приложения нет: их поведение покрыто только
  смоук-тестами раздачи. Логика, которую стоит покрыть в первую очередь, —
  `routeInstructions.ts` и `validateData.ts`: обе чистые функции.
- `data/` сейчас содержит три корпуса и шесть этажей с изображениями-
  заполнителями. Архитектура на объём не завязана, но координаты узлов при
  замене планов придётся пересчитывать.

## Частые проблемы

**Приложение не видит правку ядра.** Ядро подключается собранным:
`pnpm --filter @campus-map/core build`, либо держать рядом
`pnpm --filter @campus-map/core dev` (watch).

**Данные отдаются как HTML.** Значит запрос к `/data/...` не попал в плагин.
Проверить, что `sourceDir` в `vite.config.ts` указывает на `data/` в корне
репозитория, и прогнать `node tooling/smoke-test.mjs --app <app> --mode dev`.

**PWA-иконки битые или отсутствуют.** Ассеты в `apps/viewer/public/`
сгенерированы `tooling/generate-pwa-assets.mjs` и закоммичены, чтобы сборка
не зависела от шага кодогенерации. При смене фирменного стиля —
перезапустить генератор, а не править PNG вручную.

**`pnpm install` падает с ошибкой lock-файла.Lock-файл версионируется, и CI
ставит зависимости с `--frozen-lockfile`. После изменения зависимостей
закоммитить обновлённый `pnpm-lock.yaml`.

**Стиль строк и кодировок.** `.editorconfig` задаёт LF и UTF-8 без BOM.
Файлы данных читаются с учётом возможного BOM, но писать их нужно без него.
